
打印「监听」= 就绪，此终端别关（它会打访问日志，观察它也是练习的一部分）。

**终端 B**：发请求。三个坑（导师当堂踩过的真坑）：

1. **PowerShell 必须写 `curl.exe`**——`curl` 是 Invoke-WebRequest 的别名，行为完全不同；Git Bash / cmd 无此问题
2. **JSON body 不要直接敲在命令行里**（中文会被终端链路 GBK 化）：body 写进 **UTF-8 编码**文件，用 `--data-binary @路径` 发送；body 文件建议放 `练习/week1/_bodies/` 之类的子目录
3. `-v` 是本练习的灵魂：显示原始报文，`>` 是请求、`<` 是响应

命令模板（各题自行改造）：

```
curl.exe -v http://127.0.0.1:8000/cases
curl.exe -v -X POST http://127.0.0.1:8000/cases -H "Content-Type: application/json" --data-binary "@_bodies/body.json"
curl.exe -v -H "Authorization: Bearer secret" http://127.0.0.1:8000/report
curl.exe -v -X DELETE http://127.0.0.1:8000/cases/TC003
```

**数据在内存**：中途搞乱就 Ctrl+C 重启服务器，全部还原。**A 题建议按顺序做**（A2 创建的 TC003，A6 前还有依赖）。

## 思考题（3 道；Q2/Q3 必须表明你自己的立场）

- **Q1**：导师第一版 demo 有个真 bug：`PUT /cases/TC999`（不存在的资源）提前返回 404、没有读请求体，结果服务器访问日志出现 `Bad request syntax ('{"level":"P1"}')`。请用 **Content-Length** 和 **HTTP/1.1 长连接（keep-alive：同一条 TCP 连接上按序发多个请求）** 的知识，用自己的话讲清：残留在连接里的 body 是怎么被当成"下一条请求"的？为什么"先 `_read_body()` 再处置"（文件 70/86 行）能修好它？

- **Q2**：demo 里"凭证错"回 **403**（58 行）。但有一种观点：真实世界的惯例是——token 无效/过期 = **认不出你是谁** = 未认证，应该回 **401**；只有"知道你是谁、但不让你干"才回 403。你认为 demo 这样处理妥不妥？如果你在测一个真实系统遇到"token 错回 403"，你会提单/提建议吗？——表明立场，说理由（此题无标准答案，我听的是你的判断）。

- **Q3**：A6 你观察到：demo 的 PUT（99 行 `.update()`）实际是**局部合并**，和课堂讲的 **PUT=全量替换** 不一致（合并那其实更像 PATCH）。你认为 demo 该不该改？如果不改，这种"PUT 其名、PATCH 其实"的接口在真实项目里会给调用方和测试挖什么坑？——表明立场，说理由。
