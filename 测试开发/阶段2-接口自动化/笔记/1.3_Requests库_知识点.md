## KP1 requests = 把 curl 翻译成 Python 函数

| curl | requests |
|---|---|
| `-X POST --data-binary @body.json` | `requests.post(url, json=...)` |
| `-H "Authorization: Bearer secret"` | `headers={...}` |
| `?query=xxx`（URL 查询串） | `params={...}` |
| `-v`（看完整响应） | 返回的 **Response 对象** |

- curl 的局限：不能循环、不能断言、不能参数化、不能进 CI
- 测试定义 =「伪造请求 → 检查响应 → **自动判定**」，第三件事只有代码能干
- 公司项目接口对象层的第一个依赖

## KP2 GET 与 Response 五件套

1. **`status_code`**：int，断言写 `== 200`
2. **`json()`**：解析 JSON 响应体；**非 JSON 体抛异常**（不是返回 None）
3. **`text`**：原始字符串；**204 空体只能看它**
4. **`headers`**：响应头字典，**大小写不敏感**
5. **`url`**：**实际发出的 URL，排障第一证据**（params 拼完的真实样子）

- `params=` 自动拼接 + URL 编码
- demo S2 带 params 回 404 = 裸 `http.server` 整串 path 匹配、不解析 query 的**服务端局限**，非 requests 问题

## KP3 POST：json= vs data=（高频事故点）

- **`json=dict`**：自动序列化 + 自动加 `Content-Type: application/json`
- **`data=dict`**：发表单编码（`a=1&b=2`），Content-Type 为 `x-www-form-urlencoded`
- 服务器 `json.loads(body)` 遇到表单编码 → 解析失败 → **400**
- demo S3a（json=，201 + application/json）vs S3b（data=，400）实测对比
- 口诀：**「接口没坏，是你方言说错了」**——排查 400 先看自己发的 Content-Type
- **写后查**：POST 断言不止看 201，要再 GET 确认资源真的落库（201 → 200）

## KP4 PUT / DELETE / headers=

- **PUT**：demo 实测**合并语义**（只送 level，title 存活）= 1.2 可议点代码亲验；原则：**以文档为基准，实测不一致不许沉默**
- **DELETE**：成功回 **204 空体** → `json()` 抛异常、看 `text`；再删回 **404** = 幂等观察（**状态效果相同、响应码可不同**）
- **headers= / S6 授权三连循环**（401 → 403 → 200）= 参数化雏形，2.4 `@pytest.mark.parametrize` 正式化
- **timeout 必带**：默认永远等 = 挂死源头；S7 用 `192.0.2.1`（RFC 5737 保留段）演示快速失败
